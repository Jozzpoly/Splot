## Owner intent, corrected
The 132-part world was a **disposable experiment**. Local save/load remains a useful creative tool, but it is NOT justification for heavy persistence, migration, server libraries or immortal archives. The goal is a world one wants to build and inhabit *again*, with reliable direct manipulation and meaningful material consequences. Current Splot remains visually primitive, clumsy and far from a complete game. Do not mistake a test count for product quality.

A/B `camera=seconds` uses `1-(1-alpha60)^(60*dt)` for the same 60-Hz legacy response but stable elapsed-time behavior at 60/120/240Hz. **Legacy default unchanged.** This does NOT solve unsmoothed solver pose rendering / render interpolation.
- Render work: original `sceneTriangles(world.scene)` and repeated per-triangle `elements.find(owner)` ran for the entire authored world *every frame*. New `scene-visual-cache.mjs` caches only anchored authored geometry by **scene identity + revision**. Dynamic Box3D-authored elements are still derived each rendered frame because position can change *without revision bump*. No separate material truth, no frozen dynamic poses. Verified by tests and live Chrome smoke.

## Hard limits and next evidence
- UI is still tool-heavy and not a designed construction environment. No 3D gizmos, multi-selection, contextual resize, snap/disable snap, deliberate numeric field input, reliable multi-touch orbit, or robust drag-through-occlusion model.
- `Popraw` uses a picked surface and a constant-world-Z translation plane; an unintentional click on an overlapped surface or a camera orbit during drag may select another part. Screen selection needs its own visibility/provenance system; do not hide problems by globally forbidding overlaps.
- `Cofnij` tracks **authored edits**, not dynamic Box3D physics or arbitrary body/actor changes. Solver-controlled deletions and transitions invalidate relevant entries. No deterministic replay.
- Geometry cache is **not a performance claim**. Static mesh rebuild reduction is structurally proven, but there is no same-device timed A/B yet, no GPU timing, no mobile thermal budget and no 1k/10k object evidence. Actors/crates and general ray picking still rebuild geometric representations.
- Underlying body shape/orientation is still axis-aligned with dynamic angular rotation intentionally locked. Moving supports, structural joints/failure, full occlusion, dynamic material topology and camera interpolation are open research horizons. Avoid calling the engine general 3D material construction.
- App is a standalone bundle built from `src/next/*.mjs` and `build-next.py --check`; do not hand-merge code. `tests/verify-next.sh` is the deterministic Node gate, Actions also runs real headless Chrome. `main` and PR #3/#4 remain untouched; **PR #5 is still a research chain**, not a stable user-approved release.

## Best next move
1. Owner free-play **new disposable** structures from scratch. Does direct edit increase natural willingness to iterate? Can the user select the intended layer and change a ramp without fighting camera/controls? Compare `camera=seconds` to unchanged default on the same device; do not choose from math alone.
2. Reproduce significant remaining visual errors from the user's viewpoint: overlapping object faces, occlusion, poor material language, unclear height and selected surface. Build one coherent before/after visual scenario with independent geometry and depth assertions.
3. After selection/legibility are validated, implement a deliberately small **resize/shape-edit primitive** for existing anchored parts (including in-place numerical editing and optional snap) without punishing unusual constructions. Avoid large future-facing gizmo scaffolding before actual pressure.
4. Benchmark actual renderer CPU, GPU if available, rAF p95 and dynamic Box3D load on desktop + real phone. Only then pursue chunking/scene indexes or wider 256-part limits.

**Principle:** shorten the loop build → see → grasp → adjust → play. No more accumulating PASS-only prototypes at the expense of the feel of Splot.
